SQL 教程

从零开始系统学习 SQL 结构化查询语言，涵盖基础语法、多表操作、事务机制、索引优化和数据库设计原理。SQL 是所有关系型数据库的通用语言，掌握 SQL 是后端开发、数据分析和数据库管理的必备技能。

1. SQL 简介

原理讲解：SQL 是什么

SQL（Structured Query Language，结构化查询语言）是一种用于管理关系型数据库的标准语言。它由 IBM 的 Raymond Boyce 和 Donald Chamberlin 在 1970 年代初设计，最初叫 SEQUEL（Structured English Query Language）。

SQL 的核心特点：声明式编程——你只需要告诉数据库"想要什么"（WHAT），而不需要告诉它"怎么做"（HOW）。数据库引擎会自动选择最优的执行计划来获取结果。

SQL 的功能可以分为四大类：DDL（数据定义语言，CREATE/ALTER/DROP）、DML（数据操作语言，SELECT/INSERT/UPDATE/DELETE）、DCL（数据控制语言，GRANT/REVOKE）和 TCL（事务控制语言，COMMIT/ROLLBACK）。

SQL
-- SQL 的基本分类
-- DDL（Data Definition Language）数据定义语言
CREATE TABLE users (
    id      INT PRIMARY KEY,
    name    VARCHAR(50),
    email   VARCHAR(100)
);

-- DML（Data Manipulation Language）数据操作语言
INSERT INTO users VALUES (1, '张三', 'zhangsan@example.com');
SELECT * FROM users WHERE id = 1;
UPDATE users SET name = '李四' WHERE id = 1;
DELETE FROM users WHERE id = 1;

-- DCL（Data Control Language）数据控制语言
GRANT SELECT ON users TO 'reader'@'localhost';
REVOKE SELECT ON users FROM 'reader'@'localhost';

-- TCL（Transaction Control Language）事务控制语言
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
SQL 语句不区分大小写（关键字和标识符），但建议关键字大写、标识符小写，以提高可读性。不同数据库（MySQL、PostgreSQL、Oracle、SQL Server）在标准 SQL 基础上各有扩展。

2. 数据库基础

原理讲解：关系型数据库模型

关系型数据库基于 E.F. Codd 提出的关系模型，数据以二维表（关系）的形式组织。每张表由行（记录/tuple）和列（字段/attribute）组成。

核心概念：主键（Primary Key）唯一标识每一行记录；外键（Foreign Key）建立表与表之间的关联；候选键（Candidate Key）是可以作为主键的列或列组合。

关系型数据库遵循ACID特性：原子性（Atomicity）、一致性（Consistency）、隔离性（Isolation）、持久性（Durability），保证数据操作的可靠性。

创建与管理数据库

-- 创建数据库
CREATE DATABASE mydb
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_unicode_ci;

-- 查看所有数据库
SHOW DATABASES;

-- 使用数据库
USE mydb;

-- 查看当前数据库中的所有表
SHOW TABLES;

-- 查看表结构
DESC users;
SHOW CREATE TABLE users;

-- 删除数据库（危险操作！）
DROP DATABASE IF EXISTS mydb;

3. 数据类型

原理讲解：选择正确的数据类型

数据类型决定了列中存储的数据格式和占用空间。选择合适的数据类型对存储效率、查询性能和数据完整性至关重要。

核心原则：够用就好——使用能容纳数据的最小类型。例如，如果用户的年龄不会超过 150，用 TINYINT（1 字节）比 INT（4 字节）更合理。对于字符串，VARCHAR（变长）比 CHAR（定长）更节省空间，但 CHAR 在固定长度场景下性能略好。

4. SELECT 基础

原理讲解：查询执行流程

当你执行一条 SELECT 语句时，数据库引擎的处理流程是：FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT。理解这个顺序对于编写正确的 SQL 至关重要——比如你不能在 WHERE 中使用 SELECT 中定义的别名，因为 WHERE 在 SELECT 之前执行。

SQL
-- 基本查询
SELECT * FROM users;

-- 选择特定列
SELECT name, email FROM users;

-- 使用别名
SELECT
    name AS 用户名,
    email AS 邮箱
FROM users;

-- 去重
SELECT DISTINCT department FROM employees;

-- 运算
SELECT
    name,
    salary,
    salary * 12 AS annual_salary
FROM employees;

-- 条件拼接列
SELECT
    name,
    salary,
    CASE
        WHEN salary >= 20000 THEN '高薪'
        WHEN salary >= 10000 THEN '中等'
        ELSE '低薪'
    END AS salary_level
FROM employees;

5. WHERE 条件

原理讲解：WHERE 的执行顺序

WHERE 子句用于过滤行数据。理解 WHERE 中各条件的逻辑运算顺序很重要：NOT → AND → OR。建议始终使用括号明确优先级，避免歧义。

WHERE 中不能使用 SELECT 定义的别名（因为 SELECT 在 WHERE 之后执行），但可以使用 FROM 表中的原始列名。也不能在 WHERE 中使用聚合函数（聚合函数在 GROUP BY 之后处理）。

SQL
-- 比较运算符
SELECT * FROM employees WHERE salary > 10000;
SELECT * FROM employees WHERE age >= 18 AND age <= 60;

-- BETWEEN（包含两端）
SELECT * FROM employees WHERE salary BETWEEN 8000 AND 15000;

-- IN（匹配列表中的任意值）
SELECT * FROM employees WHERE department IN ('技术部', '产品部', '设计部');

-- LIKE（模糊匹配）
SELECT * FROM users WHERE name LIKE '张%';       -- 以"张"开头
SELECT * FROM users WHERE name LIKE '%三%';     -- 包含"三"
SELECT * FROM users WHERE name LIKE '_明';      -- 两个字，第二个是"明"

-- IS NULL / IS NOT NULL
SELECT * FROM users WHERE email IS NULL;
SELECT * FROM users WHERE email IS NOT NULL;

-- 逻辑组合（注意括号！）
SELECT * FROM employees
WHERE (department = '技术部' AND salary > 15000)
   OR (department = '产品部' AND salary > 12000);

-- EXISTS（关联子查询判断）
SELECT * FROM users u
WHERE EXISTS (
    SELECT 1 FROM orders o WHERE o.user_id = u.id
);
LIKE 以通配符开头（如 %三%）会导致索引失效，走全表扫描。如果数据量大，建议使用全文索引或搜索引擎。

6. 排序与分页

SQL
-- ORDER BY 升序（ASC，默认）/ 降序（DESC）
SELECT * FROM employees ORDER BY salary DESC;

-- 多列排序：先按部门升序，部门相同按薪资降序
SELECT * FROM employees
ORDER BY department ASC, salary DESC;

-- 按表达式排序
SELECT name, salary, salary * 12 AS annual
FROM employees
ORDER BY annual DESC;

-- 按列序号排序（不推荐，可读性差）
SELECT name, salary FROM employees ORDER BY 2 DESC;

-- LIMIT 分页（MySQL 语法）
SELECT * FROM employees ORDER BY id LIMIT 10;              -- 前10条
SELECT * FROM employees ORDER BY id LIMIT 10 OFFSET 20;   -- 跳过前20条，取10条（第3页）

-- 通用分页公式：第 page 页，每页 size 条
-- LIMIT size OFFSET (page - 1) * size
SELECT * FROM employees ORDER BY id LIMIT 20 OFFSET 40;  -- 第3页，每页20条
原理讲解：深分页问题

当 OFFSET 很大时（如 LIMIT 20 OFFSET 1000000），数据库需要先扫描并丢弃前 100 万行，再取 20 行，性能急剧下降。解决方案：游标分页（基于上一页最后一条的 ID 继续查询），避免大 OFFSET。

SQL
-- 游标分页（推荐用于大数据量）
-- 第一页
SELECT * FROM employees ORDER BY id LIMIT 20;

-- 下一页：用上一页最后一条的 ID 作为起点
SELECT * FROM employees
WHERE id > 12345   -- 上一页最后一条的 ID
ORDER BY id
LIMIT 20;

7. 聚合函数

原理讲解：聚合函数的工作方式

聚合函数将多行数据汇总为单个结果。它们在 WHERE 过滤之后、ORDER BY 排序之前执行。常用的聚合函数：COUNT（计数）、SUM（求和）、AVG（平均值）、MAX/MIN（最大/最小值）。

NULL 值处理：聚合函数会自动忽略 NULL 值（COUNT(*) 除外）。COUNT(column) 只计算非 NULL 的行，COUNT(*) 计算所有行（包括全 NULL 的行）。

SQL
-- 基本聚合
SELECT
    COUNT(*) AS total,
    COUNT(email) AS has_email,  -- 排除 NULL
    SUM(salary) AS total_salary,
    AVG(salary) AS avg_salary,
    MAX(salary) AS max_salary,
    MIN(salary) AS min_salary
FROM employees;

-- COUNT 的不同用法
SELECT COUNT(*) FROM employees;         -- 所有行
SELECT COUNT(DISTINCT department) FROM employees;  -- 不重复的部门数

-- 配合 WHERE 使用
SELECT AVG(salary) AS avg_salary
FROM employees
WHERE department = '技术部';

8. GROUP BY

原理讲解：GROUP BY 的执行逻辑

GROUP BY 将结果集按指定列的值分组，然后对每组应用聚合函数。执行顺序：WHERE → GROUP BY → 聚合函数 → HAVING → SELECT。

重要规则：SELECT 中非聚合列必须全部出现在 GROUP BY 中。例如 SELECT department, name FROM employees GROUP BY department 是非法的，因为 name 不在 GROUP BY 中且不是聚合函数。

HAVING vs WHERE：WHERE 在分组前过滤行，HAVING 在分组后过滤组。聚合条件只能放在 HAVING 中。

SQL
-- 按部门统计人数和平均薪资
SELECT
    department,
    COUNT(*) AS emp_count,
    AVG(salary) AS avg_salary
FROM employees
GROUP BY department;

-- HAVING 过滤分组结果
SELECT
    department,
    COUNT(*) AS emp_count,
    AVG(salary) AS avg_salary
FROM employees
GROUP BY department
HAVING COUNT(*) >= 5         -- 只保留人数 ≥ 5 的部门
  AND AVG(salary) > 10000;  -- 并且平均薪资 > 10000

-- WHERE + GROUP BY + HAVING 完整流程
SELECT
    department,
    COUNT(*) AS emp_count,
    AVG(salary) AS avg_salary
FROM employees
WHERE status = 'active'       -- 1. 先过滤：只看在职员工
GROUP BY department            -- 2. 分组
HAVING COUNT(*) >= 3;          -- 3. 再过滤组

-- GROUP BY 多列
SELECT
    department,
    level,
    COUNT(*) AS cnt
FROM employees
GROUP BY department, level;

-- GROUP BY + ROLLUP（小计与总计）
SELECT
    COALESCE(department, '合计') AS dept,
    SUM(salary) AS total
FROM employees
GROUP BY department WITH ROLLUP;

9. JOIN 连接

原理讲解：JOIN 的本质与执行方式

JOIN 将两张或多张表按关联条件横向拼接。不同的 JOIN 类型决定了哪些行会被保留在结果集中。

数据库引擎执行 JOIN 的常见算法：Nested Loop Join（嵌套循环，适合小表驱动）、Hash Join（哈希连接，适合等值连接大表）、Sort Merge Join（排序合并，适合已排序数据）。选择哪种算法取决于表大小、索引和统计信息。

SQL
-- INNER JOIN：只返回两表都匹配的行
SELECT
    u.name,
    o.order_id,
    o.amount
FROM users u
INNER JOIN orders o ON u.id = o.user_id;

-- LEFT JOIN：左表全部保留，右表不匹配则为 NULL
SELECT
    u.name,
    COUNT(o.order_id) AS order_count
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.id, u.name;

-- RIGHT JOIN：右表全部保留（较少用，通常改写为 LEFT JOIN）
SELECT
    u.name,
    o.order_id
FROM users u
RIGHT JOIN orders o ON u.id = o.user_id;

-- FULL OUTER JOIN：两表全部保留（MySQL 不直接支持，需 UNION 模拟）
SELECT u.name, o.order_id
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
UNION
SELECT u.name, o.order_id
FROM users u
RIGHT JOIN orders o ON u.id = o.user_id;

-- CROSS JOIN：笛卡尔积（每行 × 每行）
SELECT u.name, p.product_name
FROM users u
CROSS JOIN products p;

-- SELF JOIN：自连接
SELECT
    e.name AS employee,
    m.name AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;

-- 多表连接
SELECT
    u.name,
    o.order_id,
    oi.product_id,
    p.product_name
FROM users u
JOIN orders o ON u.id = o.user_id
JOIN order_items oi ON o.id = oi.order_id
JOIN products p ON oi.product_id = p.id;
JOIN 类型说明结果集
INNER JOIN只返回匹配的行两表交集
LEFT JOIN左表全部 + 右表匹配左表全集 + 交集
RIGHT JOIN右表全部 + 左表匹配右表全集 + 交集
FULL OUTER JOIN两表全部保留两表并集
CROSS JOIN笛卡尔积行数 = A × B
SELF JOIN表与自身连接取决于 JOIN 类型

10. 子查询

原理讲解：子查询 vs JOIN

子查询（Subquery）是嵌套在另一个 SQL 语句中的查询。分为标量子查询（返回单值）、行子查询（返回一行）和表子查询（返回多行多列）。

现代数据库优化器通常会将子查询重写为 JOIN，因为 JOIN 的执行效率通常更高。但在某些场景（如 EXISTS）下，子查询语义更清晰，且优化器处理得很好。

SQL
-- 标量子查询（返回单值）
SELECT name, salary
FROM employees
WHERE salary > (SELECT AVG(salary) FROM employees);

-- IN 子查询
SELECT * FROM users
WHERE id IN (
    SELECT user_id FROM orders WHERE amount > 1000
);

-- EXISTS（推荐用于判断存在性，通常比 IN 更快）
SELECT * FROM users u
WHERE EXISTS (
    SELECT 1 FROM orders o
    WHERE o.user_id = u.id AND o.amount > 1000
);

-- NOT EXISTS（查找没有订单的用户）
SELECT * FROM users u
WHERE NOT EXISTS (
    SELECT 1 FROM orders o WHERE o.user_id = u.id
);

-- 派生表（FROM 子句中的子查询）
SELECT
    d.department,
    d.avg_salary
FROM (
    SELECT department, AVG(salary) AS avg_salary
    FROM employees
    GROUP BY department
) d
WHERE d.avg_salary > 15000;

11. 联合查询

SQL
-- UNION：合并两个查询结果，自动去重
SELECT name, email FROM customers
UNION
SELECT name, email FROM suppliers;

-- UNION ALL：不去重（性能更好）
SELECT name FROM table_a
UNION ALL
SELECT name FROM table_b;

-- 注意：两个查询的列数和类型必须一致
-- 可以对整体结果排序（ORDER BY 放在最后）
SELECT name, email FROM customers
UNION
SELECT name, email FROM suppliers
ORDER BY name;
如果不需要去重，始终使用 UNION ALL，因为它避免了去重的排序/哈希开销，性能显著更好。

12. INSERT

SQL
-- 插入单行
INSERT INTO users (name, email, age)
VALUES ('张三', 'zhangsan@example.com', 25);

-- 插入多行
INSERT INTO users (name, email, age)
VALUES
    ('李四', 'lisi@example.com', 30),
    ('王五', 'wangwu@example.com', 28),
    ('赵六', 'zhaoliu@example.com', 35);

-- INSERT ... SELECT（从查询结果插入）
INSERT INTO users_backup (name, email, age)
SELECT name, email, age
FROM users
WHERE created_at < '2024-01-01';

-- INSERT IGNORE（忽略重复/错误）
INSERT IGNORE INTO users (id, name, email)
VALUES (1, '张三', 'zhangsan@example.com');

-- ON DUPLICATE KEY UPDATE（存在则更新）
INSERT INTO user_stats (user_id, login_count)
VALUES (1, 1)
ON DUPLICATE KEY UPDATE
    login_count = login_count + 1;

-- REPLACE INTO（存在则删除后插入）
REPLACE INTO users (id, name, email)
VALUES (1, '张三新', 'new@example.com');
批量插入时，每批建议 500-1000 行，避免单条 INSERT 过大导致事务日志膨胀和锁等待。

13. UPDATE

SQL
-- 更新单行
UPDATE users
SET email = 'new@example.com'
WHERE id = 1;

-- 更新多列
UPDATE users
SET name = '李四', age = 31
WHERE id = 2;

-- 基于表达式更新
UPDATE products
SET price = price * 1.1
WHERE category = '电子产品';

-- 多表更新（MySQL 语法）
UPDATE users u
JOIN orders o ON u.id = o.user_id
SET u.level = 'VIP'
WHERE o.total_amount > 10000;

-- LIMIT 限制更新行数
UPDATE users
SET status = 'inactive'
WHERE last_login < '2023-01-01'
LIMIT 100;
UPDATE 没有 WHERE 子句会更新所有行！执行前务必确认 WHERE 条件是否正确。建议先用 SELECT 验证影响的行。

14. DELETE

SQL
-- 删除单行
DELETE FROM users WHERE id = 1;

-- 删除多行
DELETE FROM users WHERE status = 'inactive';

-- 多表删除（MySQL 语法）
DELETE u FROM users u
JOIN orders o ON u.id = o.user_id
WHERE o.created_at < '2020-01-01';

-- TRUNCATE（快速清空表，不能回滚）
TRUNCATE TABLE temp_data;

-- DELETE vs TRUNCATE
-- DELETE：逐行删除，记录日志，可回滚，触发热触发器
-- TRUNCATE：直接释放数据页，不可回滚，重置 AUTO_INCREMENT
DELETE 和 TRUNCATE 都是危险操作。生产环境务必在事务中执行，或先备份数据。TRUNCATE 不可回滚！

软删除 vs 硬删除

原理讲解：软删除策略

软删除（Soft Delete）不真正删除数据，而是标记一个 deleted_at 时间戳。优势：数据可恢复、保留审计记录、外键约束不受影响。劣势：查询需要额外过滤、数据量持续增长。

硬删除（Hard Delete）直接 DELETE 或 TRUNCATE。优势：释放空间、查询简单。劣势：数据不可恢复、可能破坏引用完整性。

建议：核心业务数据（用户、订单）用软删除，临时数据（日志、缓存）用硬删除。

SQL
-- 软删除表设计
CREATE TABLE users (
    id         BIGINT PRIMARY KEY AUTO_INCREMENT,
    name       VARCHAR(50) NOT NULL,
    deleted_at TIMESTAMP NULL DEFAULT NULL,
    INDEX idx_deleted (deleted_at)
);

-- 软删除操作
UPDATE users SET deleted_at = NOW() WHERE id = 1;

-- 查询时自动过滤已删除的记录
SELECT * FROM users WHERE deleted_at IS NULL;

-- 创建视图简化查询
CREATE VIEW v_active_users AS
SELECT * FROM users WHERE deleted_at IS NULL;

15. 事务

原理讲解：ACID 与事务隔离级别

ACID 是事务的四大特性：

原子性（Atomicity）：事务中的操作要么全部成功，要么全部回滚。通过 undo log（回滚日志）实现——记录每个操作的逆操作，失败时反向执行 undo log 恢复数据。

一致性（Consistency）：事务执行前后，数据库从一个一致性状态转换到另一个一致性状态。这是最终目的，由 AID 共同保证。

隔离性（Isolation）：并发事务之间互不干扰。通过锁机制和 MVCC 实现。SQL 标准定义了四个隔离级别。

持久性（Durability）：事务提交后，数据永久保存。通过 redo log（重做日志）实现——事务提交时先写 redo log 再写数据页，即使宕机也能通过 redo log 恢复。

事务隔离级别

隔离级别脏读不可重复读幻读说明
READ UNCOMMITTED可能可能可能最低级别，几乎不用
READ COMMITTED不会可能可能Oracle 默认，PG 可选
REPEATABLE READ不会不会可能*MySQL InnoDB 默认
SERIALIZABLE不会不会不会最高级别，性能最差
原理讲解：MVCC 多版本并发控制

MVCC（Multi-Version Concurrency Control）是 InnoDB 实现高并发的核心机制。每行记录有两个隐藏列：trx_id（最近修改的事务 ID）和 roll_pointer（指向 undo log 中旧版本的指针）。

读操作通过ReadView（一致性视图）判断哪些版本对当前事务可见：在 RC 级别下，每次 SELECT 都生成新的 ReadView；在 RR 级别下，只在第一次 SELECT 时生成 ReadView，之后复用。这就是为什么 RR 级别能避免不可重复读。

MVCC 的优势：读写不阻塞——普通 SELECT 不加锁，可以和 INSERT/UPDATE/DELETE 并发执行，大幅提升并发性能。

-- 显式事务
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;

-- 出错时回滚
BEGIN;
UPDATE accounts SET balance = balance - 5000 WHERE id = 1;
-- 检查余额是否足够
SELECT balance FROM accounts WHERE id = 1;
-- 如果不足，回滚
ROLLBACK;

-- 设置隔离级别

-- 保存点（SAVEPOINT）—— 部分回滚
BEGIN;
INSERT INTO users VALUES (1, '张三');
SAVEPOINT sp1;
INSERT INTO users VALUES (2, '李四');
ROLLBACK TO sp1;   -- 只回滚第二条
COMMIT;             -- 第一条生效
原理讲解：InnoDB 锁机制

InnoDB 使用行级锁而非表锁，大幅提升并发性能。锁的类型包括：

Record Lock（记录锁）：锁定索引上的单条记录。Gap Lock（间隙锁）：锁定索引记录之间的间隙，防止其他事务插入，解决幻读问题。Next-Key Lock（临键锁）：Record Lock + Gap Lock 的组合，是 InnoDB 在 RR 级别下的默认加锁方式。

死锁处理：InnoDB 通过等待图（wait-for graph）检测死锁，自动回滚代价较小的事务。可以通过 SHOW ENGINE INNODB STATUS 查看最近的死锁信息。

16. 表设计

原理讲解：表设计的核心原则

好的表设计是数据库性能的基石。核心原则：选择合适的主键（自增 INT 或雪花算法 BIGINT）、合理使用数据类型（够用就好）、适度冗余（减少 JOIN）、预留扩展字段。

自增 ID 的优势：有序插入，B+Tree 叶子节点顺序分裂，写入性能好。缺点：暴露业务量（可被遍历）、分库分表后可能冲突。雪花 ID 的优势：全局唯一、有序、不依赖数据库。缺点：存储空间大（8 字节）、无业务含义。

17. 约束与索引

原理讲解：B+Tree 索引原理

InnoDB 使用B+Tree作为索引数据结构。B+Tree 的特点：所有数据都存储在叶子节点，叶子节点通过双向链表连接，便于范围查询。

聚簇索引（主键索引）：叶子节点存储完整的行数据。一张表只有一个聚簇索引（就是主键）。数据行按照主键顺序物理存储。

二级索引（非聚簇索引）：叶子节点存储的是主键值。通过二级索引查找数据时，先在二级索引中找到主键值，再通过主键索引找到完整行数据，这个过程叫回表。

覆盖索引：如果查询所需的所有列都包含在某个索引中，就不需要回表，大幅提升查询性能。EXPLAIN 中的 Using index 就表示使用了覆盖索引。

最左前缀原则：联合索引 (a, b, c) 可以被 WHERE a=1 / WHERE a=1 AND b=2 / WHERE a=1 AND b=2 AND c=3 使用，但不能被 WHERE b=2 或 WHERE b=2 AND c=3 使用（不满足最左前缀）。

约束类型

SQL
-- PRIMARY KEY：主键（唯一 + 非空）
id INT PRIMARY KEY,

-- UNIQUE：唯一约束
email VARCHAR(100) UNIQUE,

-- NOT NULL：非空约束

-- DEFAULT：默认值

-- CHECK：检查约束（MySQL 8.0+ 支持）

salary DECIMAL(10,2) CHECK (salary > 0),

-- FOREIGN KEY：外键约束

    ON DELETE CASCADE
    ON UPDATE CASCADE,

-- AUTO_INCREMENT：自增
id BIGINT PRIMARY KEY AUTO_INCREMENT,

-- COMMENT：列注释
remark VARCHAR(200) COMMENT '备注';

CREATE UNIQUE INDEX idx_email ON users(email);

18. 视图

原理讲解：视图的本质

视图（View）是一个虚拟表，它的内容由查询语句定义。视图不存储实际数据，每次访问视图时，数据库会执行底层的 SELECT 语句。

视图的主要作用：简化复杂查询（将常用多表 JOIN 封装为视图）、权限控制（只暴露特定列给特定用户）、数据安全（隐藏敏感字段）。

MySQL 的视图分为普通视图（每次都重新计算）和物化视图（PostgreSQL 支持，将结果缓存到磁盘，但需要定期刷新）。

SQL
-- 创建视图
CREATE VIEW v_user_orders AS
SELECT
    u.id,
    u.name,
    COUNT(o.id) AS order_count,
    IFNULL(SUM(o.amount), 0) AS total_amount
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.id, u.name;

-- 使用视图（像普通表一样查询）
SELECT * FROM v_user_orders
WHERE total_amount > 1000;

-- 修改视图
ALTER VIEW v_user_orders AS
SELECT
    u.id,
    u.name,
    COUNT(o.id) AS order_count
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.id, u.name;

-- 删除视图
DROP VIEW IF EXISTS v_user_orders;

19. 存储过程

原理讲解：存储过程的利弊

存储过程（Stored Procedure）是预编译的 SQL 代码块，存储在数据库服务器端。优势：减少网络传输（一次调用多条 SQL）、预编译执行更快、封装业务逻辑。

劣势：调试困难、版本管理麻烦（难以纳入 Git）、可移植性差（不同数据库语法不同）、扩展性受限（水平扩展困难）。现代应用开发中，大多数团队更倾向于将业务逻辑放在应用层，只将简单的数据操作留给数据库。

SQL
-- 创建存储过程：转账操作
DELIMITER //
CREATE PROCEDURE sp_transfer(
    IN from_id INT,
    IN to_id INT,
    IN amount DECIMAL(10,2)
)
BEGIN
    DECLARE balance DECIMAL(10,2);

    -- 检查余额
    SELECT balance INTO balance
    FROM accounts
    WHERE id = from_id
    FOR UPDATE;   -- 加行锁防止并发

    IF balance < amount THEN
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = '余额不足';
    END IF;

    -- 执行转账
    UPDATE accounts SET balance = balance - amount WHERE id = from_id;
    UPDATE accounts SET balance = balance + amount WHERE id = to_id;

    -- 记录流水
    INSERT INTO transactions (from_id, to_id, amount)
    VALUES (from_id, to_id, amount);
END //
DELIMITER ;

-- 调用存储过程
CALL sp_transfer(1, 2, 100.00);

20. 窗口函数

原理讲解：窗口函数 vs 聚合函数

窗口函数（Window Function）对一组相关行执行计算，但不折叠行（不像 GROUP BY）。每行都能看到计算结果，同时保留原始行。

语法：函数名() OVER (PARTITION BY 分组列 ORDER BY 排序列 ROWS/RANGE 帧范围)

窗口函数在 GROUP BY 之后、ORDER BY 之前执行。它解决了"每组取 Top N"、"累计求和"、"移动平均"等聚合函数难以处理的问题。

SQL
-- 排名函数
SELECT
    name, department, salary,
    ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS rn,
    RANK()       OVER (PARTITION BY department ORDER BY salary DESC) AS rnk,
    DENSE_RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS drnk
FROM employees;

-- ROW_NUMBER：严格递增（1,2,3）
-- RANK：有并列（1,2,2,4）  -- 跳过名次
-- DENSE_RANK：有并列（1,2,2,3）-- 不跳过名次

-- 累计求和
SELECT
    order_date, amount,
    SUM(amount) OVER (ORDER BY order_date) AS cumulative_sum
FROM orders;

-- 移动平均（当前行 + 前后各1行，共3行）
SELECT
    order_date, amount,
    AVG(amount) OVER (
        ORDER BY order_date
        ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING
    ) AS moving_avg
FROM orders;

-- LAG / LEAD：获取前/后 N 行的值
SELECT
    month, revenue,
    LAG(revenue, 1)  OVER (ORDER BY month) AS prev_month,
    LEAD(revenue, 1) OVER (ORDER BY month) AS next_month,
    revenue - LAG(revenue, 1) OVER (ORDER BY month) AS growth
FROM monthly_sales;

-- NTILE：将数据分成 N 组
SELECT
    name, salary,
    NTILE(4) OVER (ORDER BY salary DESC) AS quartile
FROM employees;

窗口函数实战场景

SQL
-- 场景1：计算环比增长率
WITH monthly AS (
    SELECT
        DATE_FORMAT(created_at, '%Y-%m') AS month,
        SUM(amount) AS revenue
    FROM orders
    GROUP BY DATE_FORMAT(created_at, '%Y-%m')
)
SELECT
    month,
    revenue,
    LAG(revenue, 1) OVER (ORDER BY month) AS prev_revenue,
    ROUND(
        (revenue - LAG(revenue, 1) OVER (ORDER BY month))
        * 100.0 / LAG(revenue, 1) OVER (ORDER BY month),
        2
    ) AS growth_rate_pct
FROM monthly
ORDER BY month;

-- 场景2：每组取 Top 3（经典面试题）
WITH ranked AS (
    SELECT
        category, product_name, sales,
        ROW_NUMBER() OVER (
            PARTITION BY category
            ORDER BY sales DESC
        ) AS rn
    FROM products
)
SELECT * FROM ranked WHERE rn <= 3;

-- 场景3：用户连续登录天数统计
WITH user_dates AS (
    SELECT DISTINCT
        user_id,
        DATE(login_time) AS login_date
    FROM user_logins
),
grouped AS (
    SELECT
        user_id,
        login_date,
        DATE_SUB(login_date,
            INTERVAL ROW_NUMBER() OVER (
                PARTITION BY user_id ORDER BY login_date
            ) DAY
        ) AS grp
    FROM user_dates
)
SELECT
    user_id,
    MIN(login_date) AS start_date,
    MAX(login_date) AS end_date,
    COUNT(*) AS consecutive_days
FROM grouped
GROUP BY user_id, grp
HAVING COUNT(*) >= 3
ORDER BY consecutive_days DESC;

21. 查询优化

原理讲解：EXPLAIN 与执行计划

使用 EXPLAIN 分析查询的执行计划是优化 SQL 的第一步。关键关注以下字段：

type（访问类型，从好到差）：system > const > eq_ref > ref > range > index > ALL。如果出现 ALL（全表扫描），说明需要优化。

key：实际使用的索引。如果为 NULL，说明没有使用索引。

rows：预估扫描的行数。越小越好。

Extra：Using index（覆盖索引，好）、Using temporary（使用临时表，需关注）、Using filesort（文件排序，需关注）。

SQL
-- EXPLAIN 分析查询
EXPLAIN SELECT * FROM employees
WHERE department = '技术部' AND salary > 15000;

-- EXPLAIN FORMAT=JSON 获取更详细的信息
EXPLAIN FORMAT=JSON SELECT * FROM employees
WHERE department = '技术部';

-- 常见优化技巧

-- 1. 避免 SELECT *
-- 不推荐：
SELECT * FROM users WHERE id = 1;
-- 推荐：
SELECT id, name, email FROM users WHERE id = 1;

-- 2. 避免在索引列上使用函数
-- 不推荐（索引失效）：
SELECT * FROM orders WHERE YEAR(created_at) = 2024;
-- 推荐（使用范围查询）：
SELECT * FROM orders
WHERE created_at >= '2024-01-01'
  AND created_at < '2025-01-01';

-- 3. 使用覆盖索引避免回表
-- 如果有索引 (department, salary)，以下查询不需要回表：
SELECT department, salary FROM employees
WHERE department = '技术部';

-- 4. 小表驱动大表（JOIN 时小表做驱动表）
-- 如果 users 有1万行，orders 有100万行：
SELECT u.name, o.order_id
FROM users u       -- 小表做驱动表
JOIN orders o ON u.id = o.user_id;

-- 5. 使用 UNION ALL 替代 UNION（不需要去重时）
-- 6. 批量操作代替逐条操作
-- 7. 合理使用 LIMIT 减少返回数据量
索引失效的常见场景：LIKE '%xxx'（左模糊）、对索引列使用函数或运算、OR 条件中非索引列、类型隐式转换、NOT IN / NOT EXISTS（部分场景）。

22. 范式与反范式

原理讲解：三大范式

第一范式（1NF）：每列都是原子值，不可再分。例如"地址"列不应同时存储省、市、区，应拆分为独立的列。

第二范式（2NF）：在 1NF 基础上，非主键列必须完全依赖于主键（消除部分依赖）。例如，订单详情表中"商品名称"只依赖于 product_id，不依赖于 order_id，应拆分为商品表。

第三范式（3NF）：在 2NF 基础上，非主键列不能传递依赖于主键。例如，员工表中有 department_id → department_name，department_name 传递依赖于员工主键，应拆分为部门表。

原理讲解：反范式设计

严格遵循范式会导致频繁的 JOIN 操作，在读多写少的场景下可能影响查询性能。反范式通过适当冗余数据来减少 JOIN，用空间换时间。

常见反范式手段：冗余列（在订单表中冗余用户名，避免每次查询都 JOIN 用户表）、派生列（在用户表中维护 order_count，避免 COUNT 查询）、预计算列（物化视图、汇总表）。

原则：读多写少可以适当反范式；写多读少应该严格范式化；OLAP 场景可以大量反范式（数据仓库的星型/雪花模型就是典型的反范式设计）。

SQL
-- 范式化设计示例
CREATE TABLE departments (
    id   INT PRIMARY KEY,
    name VARCHAR(50) NOT NULL
);

CREATE TABLE employees (
    id            INT PRIMARY KEY,
    name          VARCHAR(50) NOT NULL,
    department_id INT NOT NULL,
    FOREIGN KEY (department_id) REFERENCES departments(id)
);

-- 反范式设计：冗余部门名称，避免 JOIN
CREATE TABLE employees_denorm (
    id              INT PRIMARY KEY,
    name            VARCHAR(50) NOT NULL,
    department_id   INT NOT NULL,
    department_name VARCHAR(50) NOT NULL,  -- 冗余字段
    INDEX idx_dept (department_id)
);

24. 最佳实践

永远不要在生产环境执行不带 WHERE 的 UPDATE/DELETE。操作前先用 SELECT 验证影响的行数。重要操作使用事务包裹。定期备份数据。

命名表名和列名用小写+下划线跨数据库兼容性好
命名表名用复数或单数保持一致统一规范
类型金额用 DECIMAL，不用 FLOAT避免精度问题

索引单表索引不超过 5-6 个避免写入性能下降

事务事务尽量短小减少锁持有时间
事务避免在事务中做耗时操作如远程调用、文件读写
安全永远使用参数化查询防止 SQL 注入
安全最小权限原则应用账号只授予必要权限

25. 递归公用表表达式（CTE）

原理讲解：递归 CTE 的执行机制

递归 CTE 由两部分组成：锚点成员（Anchor Member）和递归成员（Recursive Member）。锚点成员提供初始结果集，递归成员反复引用 CTE 自身，直到不再产生新行为止。

语法：WITH RECURSIVE cte AS (锚点 UNION ALL 递归) SELECT * FROM cte。大多数数据库支持 MAXRECURSION（SQL Server）或 max_recursion_depth（MySQL）来防止无限递归。

SQL
-- 生成数字序列（1 到 100）
WITH RECURSIVE nums AS (
    SELECT 1 AS n          -- 锚点：起始值
    UNION ALL
    SELECT n + 1 FROM nums  -- 递归：引用自身
    WHERE n < 100          -- 终止条件
)
SELECT n FROM nums;

-- 遍历组织架构树
CREATE TABLE employees (
    id INT PRIMARY KEY,
    name VARCHAR(50),
    manager_id INT
);

WITH RECURSIVE org_tree AS (
    -- 锚点：CEO（无上级）
    SELECT id, name, manager_id, 0 AS level,
           CAST(name AS VARCHAR(500)) AS path
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    -- 递归：逐层查找下属
    SELECT e.id, e.name, e.manager_id, t.level + 1,
           CONCAT(t.path, ' → ', e.name)
    FROM employees e
    INNER JOIN org_tree t ON e.manager_id = t.id
)
SELECT
    REPEAT('  ', level) || name AS org_chart,
    level,
    path
FROM org_tree
ORDER BY path;

-- 生成日期序列（按月）
WITH RECURSIVE months AS (
    SELECT DATE('2024-01-01') AS month_date
    UNION ALL
    SELECT DATE_ADD(month_date, INTERVAL 1 MONTH)
    FROM months
    WHERE month_date < DATE('2024-12-01')
)
SELECT month_date, DATE_FORMAT(month_date, '%Y-%m') AS ym
FROM months;

-- ===== PIVOT：行转列 =====

-- 原始数据（行格式）
-- student_id | subject | score
-- 1          | 语文    | 90
-- 1          | 数学    | 85
-- 1          | 英语    | 92

-- MySQL 手动 PIVOT（使用 CASE + 聚合）
SELECT
    student_id,
    MAX(CASE WHEN subject = '语文' THEN score END) AS chinese,
    MAX(CASE WHEN subject = '数学' THEN score END) AS math,
    MAX(CASE WHEN subject = '英语' THEN score END) AS english
FROM scores
GROUP BY student_id;

-- SQL Server PIVOT 语法
SELECT student_id, 语文, 数学, 英语
FROM scores
PIVOT (
    MAX(score) FOR subject IN (语文, 数学, 英语)
) p;

-- 动态 PIVOT（MySQL，需要 prepared statement）
SET @sql = NULL;
SELECT
    GROUP_CONCAT(DISTINCT
        CONCAT('MAX(CASE WHEN subject = ''', subject,
               ''' THEN score END) AS `', subject, '`')
    ) INTO @sql
FROM scores;

SET @sql = CONCAT('SELECT student_id, ', @sql,
    ' FROM scores GROUP BY student_id');

PREPARE stmt FROM @sql;
EXECUTE stmt;
DEALLOCATE PREPARE stmt;

-- ===== UNPIVOT：列转行 =====

-- MySQL 手动 UNPIVOT（使用 UNION ALL）
SELECT student_id, '语文' AS subject, chinese AS score FROM pivoted
UNION ALL
SELECT student_id, '数学', math FROM pivoted
UNION ALL
SELECT student_id, '英语', english FROM pivoted;

-- SQL Server UNPIVOT 语法
SELECT student_id, subject, score
FROM pivoted
UNPIVOT (
    score FOR subject IN (语文, 数学, 英语)
) u;

27. LATERAL JOIN

SQL
-- LATERAL JOIN 允许子查询引用前面的表
-- 每个用户最近3笔订单（MySQL 8.0+ / PostgreSQL）
SELECT
    u.id,
    u.name,
    o.order_id,
    o.amount,
    o.created_at
FROM users u
JOIN LATERAL (
    SELECT order_id, amount, created_at
    FROM orders
    WHERE user_id = u.id
    ORDER BY created_at DESC
    LIMIT 3
) o ON 1 = 1;

-- 每个部门薪资最高的员工
SELECT
    d.department_name,
    e.name,
    e.salary
FROM departments d
JOIN LATERAL (
    SELECT name, salary
    FROM employees
    WHERE department_id = d.id
    ORDER BY salary DESC
    LIMIT 1
) e ON 1 = 1;

-- LATERAL 与 LEFT JOIN 配合（保留无数据的行）
SELECT
    u.name,
    COALESCE(o.recent_order, '无订单')
FROM users u
LEFT JOIN LATERAL (
    SELECT CONCAT('订单#', order_id, ' ¥', amount) AS recent_order
    FROM orders
    WHERE user_id = u.id
    ORDER BY created_at DESC
    LIMIT 1
) o ON 1 = 1;
原理讲解：LATERAL JOIN vs 子查询

普通子查询是独立执行的，不能引用外层表的列。LATERAL JOIN 让子查询可以像函数一样对外层每一行执行一次，类似于 for each row in outer_table, run inner_query。

典型场景："每组取 Top N"、"最近 N 条记录"、"每个用户的最新评论"。在没有 LATERAL 的数据库中，通常需要窗口函数 + 子查询来实现类似效果。

31. 数据仓库概念（星型模型）

原理讲解：星型模型 vs 雪花模型

星型模型（Star Schema）：一个事实表（Fact Table）连接多个维度表（Dimension Table），维度表不做进一步规范化。查询简单、JOIN 少、性能好，但存在数据冗余。

雪花模型（Snowflake Schema）：维度表进一步规范化，减少冗余但增加 JOIN 复杂度。适合维度数据量大、需要严格一致性分析的场景。

事实表存储度量值（销售额、数量等数值），维度表存储描述性属性（产品名称、时间、地区等）。

SQL
-- 星型模型示例：电商销售数据仓库

-- 事实表
CREATE TABLE fact_sales (
    sale_id     BIGINT PRIMARY KEY,
    date_id     INT NOT NULL,
    product_id  INT NOT NULL,
    customer_id INT NOT NULL,
    store_id    INT NOT NULL,
    quantity    INT NOT NULL,
    unit_price  DECIMAL(10,2),
    total_amount DECIMAL(12,2),
    FOREIGN KEY (date_id) REFERENCES dim_date(date_id),
    FOREIGN KEY (product_id) REFERENCES dim_product(product_id),
    FOREIGN KEY (customer_id) REFERENCES dim_customer(customer_id)
);

-- 维度表
CREATE TABLE dim_date (
    date_id    INT PRIMARY KEY,
    full_date  DATE,
    year       INT,
    quarter    INT,
    month      INT,
    month_name VARCHAR(10),
    day_of_week VARCHAR(10),
    is_weekend BOOLEAN
);

CREATE TABLE dim_product (
    product_id    INT PRIMARY KEY,
    product_name  VARCHAR(100),
    category      VARCHAR(50),
    brand         VARCHAR(50),
    unit_cost     DECIMAL(10,2)
);

-- 数据仓库典型查询
SELECT
    d.year,
    d.quarter,
    p.category,
    SUM(f.total_amount) AS revenue,
    SUM(f.quantity) AS units_sold,
    COUNT(DISTINCT f.customer_id) AS unique_customers
FROM fact_sales f
JOIN dim_date d ON f.date_id = d.date_id
JOIN dim_product p ON f.product_id = p.product_id
GROUP BY d.year, d.quarter, p.category
ORDER BY d.year, d.quarter, revenue DESC;

-- 找出连续 ID 中的缺失值
WITH ids AS (
    SELECT id FROM users
),
all_nums AS (
    SELECT GENERATE_SERIES(
        (SELECT MIN(id) FROM ids),
        (SELECT MAX(id) FROM ids)
    ) AS num  -- PostgreSQL
)
SELECT num AS missing_id
FROM all_nums
WHERE num NOT IN (SELECT id FROM ids);

-- ===== 累计求和（Running Total）=====
SELECT
    order_date,
    amount,
    SUM(amount) OVER (ORDER BY order_date) AS running_total
FROM orders;

-- ===== 中位数（Median）=====
-- PostgreSQL
SELECT PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY salary) AS median
FROM employees;

-- MySQL 中位数
WITH ranked AS (
    SELECT salary,
           ROW_NUMBER() OVER (ORDER BY salary) AS rn,
           COUNT(*) OVER () AS total
    FROM employees
)
SELECT AVG(salary) AS median
FROM ranked
WHERE rn IN (FLOOR((total + 1) / 2), CEIL((total + 1) / 2));

-- ===== 同比/环比增长率 =====
WITH monthly AS (
    SELECT
        DATE_FORMAT(created_at, '%Y-%m') AS month,
        SUM(amount) AS revenue
    FROM orders
    GROUP BY DATE_FORMAT(created_at, '%Y-%m')
)
SELECT
    month,
    revenue,
    LAG(revenue, 1) OVER (ORDER BY month) AS prev_month,
    ROUND((revenue - LAG(revenue, 1) OVER (ORDER BY month))
        * 100.0 / LAG(revenue, 1) OVER (ORDER BY month), 2) AS mom_growth_pct
FROM monthly
ORDER BY month;

    login_date,
    COUNT(DISTINCT user_id) OVER (
        ORDER BY login_date
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS cumulative_users
FROM user_logins;
